# LodgeFlow Phase 6 V03 and O01 Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development to execute one numbered slice at a time. Each slice gets its own focused verification and review before the next slice. The controller runs the whole-change review and final gates.

**Goal** Bring the remaining LodgeFlow JSON readers and admin test infrastructure up to the Phase 6 standards while preserving established route, accounting and UI behavior. First close the isolated optional-payment-method regression recorded by the completed Phase 4 review.

**Architecture** Validate application HTTP JSON where it enters a reader, before it reaches a cache, form success handler, or navigation. Reuse existing route DTOs, serializers and equivalent response fragments. Keep provider input, provider acknowledgement and application responses at their own boundaries. Gate admin tests and scripts independently from the Next application compiler.

**Tech stack** Node 22, pnpm 11.17.0, TypeScript 5.9.3, installed Zod 4.4.3, Next App Router, SWR, TanStack Query, Jest, disposable MongoDB and existing signed Clerk/Stripe HTTP harness.

**Spec** `AGENTS.md`, `docs/refactoring/plan.md#phase-6--remaining-debt-and-milestone-verification`, `docs/refactoring/inventory.md` V03/O01 and `docs/refactoring/inventory-current.json`. ## Global constraints

- Feature freeze and existing scope apply. Preserve HTTP statuses, envelope/acknowledgement variants, error messages, pagination placement, raw compatibility where a caller deliberately supports it, string IDs/timestamps, nullable references, sparse legacy values, additive response fields and supported cache/retry behavior.
- Parse unknown JSON with app-local Zod schemas or explicit existing guards. Use safe validation of preserved output when Zod's projected output would strip additive fields. Success predicates need evidence for the fields consumers use. Avoid request limits/defaults as read constraints. Preserve signed raw bodies, settlement, refund/receipt idempotency and all authorization/ownership and concurrency boundaries.
- No unsafe assertion shortcuts, suppressed diagnostics, disabled strict rules, new browser E2E framework, dependency upgrades, live mutations, or deployment activity. Use only disposable test databases and mocked/local Clerk, Stripe and Resend. Issues #136 and #139 remain outside the milestone.
- Use one implementation owner and one review per task. Worker scope includes listed files and directly affected fixture consumers only. Distinguish failure fixtures from real success fixtures and document any intentionally corrected malformed-response behavior. Preserve unrelated changes and user files.
- Record characterization, failing regressions where applicable, focused passing checks, and remaining inventory. Run workspace gates required by AGENTS.md before creating a PR. Human/hosted acceptance requires its own recorded evidence.

### Review focus

- A customer detail response with a deleted cabin remains readable and retains legacy/additive nested fields (Task 1).
- Strict TS passes only after real types describe included fixtures and helpers (Task 2); the separate enforcement also catches explicit type escapes accepted by the compiler (Task 20).
- An invalid body mid-refresh cannot replace last-good data or, in a denied private confirmation read, revive it on remount (Tasks 1, 8, 11, 15).
- Payment mechanisms retain real outcome and retry semantics. Malformed successful responses do not clear an in-flight token or navigate (Tasks 12 and 17).
- Stripe-signed no-op and duplicate events still acknowledge, while failed work remains retryable with sanitized verification diagnostics (Task 19).
